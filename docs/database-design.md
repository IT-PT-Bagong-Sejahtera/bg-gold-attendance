# MySQL Database Design

## Conventions

- MySQL 8, InnoDB, `utf8mb4`, and versioned SQL migrations.
- Primary keys are UUID-compatible `BINARY(16)` values generated by the application.
- Timestamps are `DATETIME(6)` in UTC. Every API/worker connection forces the MySQL session timezone to `+00:00`, including schema defaults that use `CURRENT_TIMESTAMP`.
- Monetary values use `DECIMAL`; durations use integer minutes or seconds.
- Soft deletion is limited to administrative master data. Attendance and audit data are append-only.
- Every organization-owned table includes and indexes `organization_id`.

## Identity and tenancy

- `users`: login identity, password hash, locale, status.
- `organizations`: legal/display name, timezone, attendance defaults.
- `organization_memberships`: user, employee number, status, active period.
- `roles`, `permissions`, `role_permissions`, `membership_roles`: RBAC.
- `refresh_sessions`: token-family state, hashed current token, device, expiry, revocation.
- `password_reset_tokens`: hashed one-time tokens.

## Workforce and scheduling

- `sections`: outlet/work-location identity, address, timezone override.
- `section_memberships`: eligible employees and local role.
- `shift_roles`: operational roles used by schedules.
- `shifts`: draft/published shift header and time range.
- `shift_assignments`: employee assignment and acknowledgment.
- `shift_requests`: open-shift or swap request state.
- `attendance_policies` stores early/late clock-in and clock-out tolerances, independent prevention flags, the current shift-relative scheduled-break window, separate outside-window rejection/approval behavior, and rounding controls; per-shift multi-break rows remain planned for richer schedules.

## Attendance policy

- `attendance_policies`: named versioned policy, default mode, timing windows, approval behavior.
- `attendance_policy_modes`: combinable modes such as ANYWHERE, LOCATION_ONLY, GEOFENCE, DYNAMIC_QR, WIFI, SELFIE, FACE_VERIFICATION, and DEVICE_INTEGRITY.
- `policy_assignments`: organization, section, or employee override with validity range.
- `geofences`: center, radius, and minimum accepted accuracy.
- `wifi_rules`: normalized SSID and optional hashed BSSID.
- `dynamic_qr_nonces`: signed-token nonce, expiry, and consumed timestamp.

Resolution order is employee assignment, section assignment, then organization default. The resolved policy ID and immutable snapshot are stored with every attendance event.

## Attendance

- `attendance_state`: one row per organization membership, locked during clock mutations.
- `attendance_events`: immutable clock, break, automatic, request, and correction events.
- Daily timesheets are computed from approved immutable events and their latest append-only correction. Break duration is rounded to the nearest configured increment (half increments round upward); the original event timestamps and actual duration remain unchanged.
- `attendance_evidence`: location, accuracy, network, integrity verdict, and object references.
- `face_enrollments` and `face_verifications`: provider-neutral subject enrollment plus short-lived score/liveness decisions; provider image references stay in private attachment storage.
- `attendance_requests`: pending approval state and reason.
- `attendance_decisions`: approval/rejection actor, timestamp, reason, and resulting event.
- `attendance_corrections`: original event reference and replacement meaning without deleting history.
- `idempotency_keys`: actor, scope, key, request hash, response, and expiry; unique by actor/scope/key.

Critical constraints include a unique active attendance state per membership and unique automatic-event source keys. API transactions lock `attendance_state` and the applicable idempotency row.

## Files, communication, and audit

- `attachments`: object key, owner, purpose, content type, size, checksum, finalized time, retention date, and deletion time. The retention worker removes the private object before marking metadata deleted; referenced business records remain auditable but can no longer resolve the evidence.
- `device_registrations`: organization/user-scoped platform, SHA-256 installation identifier, optional push token and its deduplication hash, last-seen time, and revocation state.
- `announcements`, `announcement_audiences`, `announcement_receipts`.
- `notification_outbox`: transactional notification intents.
- `audit_logs`: organization, actor, action, resource, before/after-safe metadata, request ID, timestamp.

Announcement publication creates immutable audience rows, one receipt per resolved membership, one inbox notification per recipient, and one notification outbox row in a single transaction. The outbox state machine is `PENDING → PROCESSING → SENT`, with bounded `FAILED` retries. Device installations are deduplicated per organization/user without storing their raw installation identifier. Optional push tokens are independently deduplicated by an organization-scoped SHA-256 hash and can be revoked without deleting historical notifications or attendance evidence.

## Leave

- `leave_types`: organization-scoped code, name, paid flag, and lifecycle status.
- `leave_balances`: unique membership/type/year entitlement with separately locked used and pending amounts.
- `leave_requests`: immutable requested range, weekday total, reason, and request state.
- `leave_request_allocations`: per-year allocation for cross-year requests, used to update balances atomically.
- `leave_decisions`: append-only manager decisions with reason and actor.

Balance rows are locked during submission and decision transactions. Approval moves reserved days from pending to used; rejection and withdrawal release the reservation without deleting the request or its history.

## Later modules

- Reporting uses indexed transactional views initially; a reporting store is considered only after measured need.

## Claims

- `claim_types`: organization category, receipt requirement, and lifecycle status.
- `claims`: employee, type, unique private receipt, amount/currency, incurred date, notes, state, and explicit OCR state.
- `claim_decisions`: append-only reviewer decision, reason, actor, and time.

Attachment ownership and single-use constraints are checked in the same transaction as claim creation. Withdrawal and manager decisions update only the state while preserving source values, receipt linkage, audit history, and append-only decisions.
